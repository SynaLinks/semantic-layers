# Sharing semantic layers

Semantic layers are shared the way Agent Skills are: as folders in git
repositories, installed with one command. The command, `semantic-layers`, is a
Python tool run with [uv](https://docs.astral.sh/uv/) — nothing to install
beyond `uv`.

!!! note "Not on PyPI yet"
    Run it from a checkout of this repository:
    `uvx --from <path-to-checkout> semantic-layers ...`.

## Installing

```shell
uvx semantic-layers add SynaLinks/semantic-layers              # every layer of the repository
uvx semantic-layers add SynaLinks/semantic-layers --layer sales
uvx semantic-layers add SynaLinks/semantic-layers --list       # its layers and their definitions
uvx semantic-layers add https://git.example.com/data/layer.git          # any git URL
uvx semantic-layers add ./path/to/layers                                # a local folder
```

`add` fetches the source, copies the layer folders into `.agents/layers/`,
verifies each with synalog, and records them in `semantic-layers-lock.json`
(at the project's root; `~/.agents/semantic-layers-lock.json` with
`--global`). Commit the lock file so teammates and CI resolve the same
layers.

What `add` guarantees:

- **Nothing unverified lands.** Every layer is checked with synalog before the
  copy; if anything fails, nothing is installed.
- **Your tables stay yours.** Installing or updating a layer you already
  connected keeps its tables and its connection: only its concepts and rules
  are replaced, and they must verify against your tables — a table or column
  your database lacks is listed.
- **No silent overwrite.** A layer folder you wrote or changed is refused
  unless you pass `--force`.

## Connecting

```shell
uvx semantic-layers connect sales psql host=db.example.com database=sales user=analyst password=...
```

This writes `synalog.toml` (the fields), `.env` (the password) and `.gitignore` into
`.agents/layers/sales/` (see [Connection](specification.md#connection)), then
generates one file per table of the database with `synalog introspect`,
keeping the descriptions and keywords already written. A table the layer has
but the database doesn't is kept and reported, since definitions may still
import it. Then the layer is checked: a concept or rule using a table or
column your database lacks is listed.

Then any definition runs from the layer's folder:

```shell
cd .agents/layers/sales
uvx synalog rules/ActiveCustomer.l run ActiveCustomer
```

## Publishing

Start a layer project with `init`:

```shell
uvx semantic-layers init sales      # or, in an empty repository: uvx semantic-layers init
```

```
sales/
├── tables/         # generated by connect
├── concepts/
├── rules/
├── synalog.toml    # the database it runs on, written by connect
├── .gitignore      # .env (the secrets), bigquery-credentials.json
└── README.md       # what the layer is, how to install and develop it
```

It also runs `git init` when the folder isn't in a repository yet, and never
overwrites a file that exists. The name is the folder's: lowercase letters,
numbers and hyphens. Inside a layer project, `connect` and `check` take the
folder's path: `semantic-layers connect . psql host=... user=...`,
`semantic-layers check .`.

A layer is published by pushing its folder to a git repository. A repository
is either one layer — `tables/`, `concepts/`, `rules/` at its root, named
after the repository — or several, one folder each, at its root or under
`layers/` or `.agents/layers/`:

```
semantic-layers/layers/
├── sales/
│   ├── tables/
│   ├── concepts/
│   └── rules/
└── support/
    ├── tables/
    └── rules/
```

The secrets never travel: `.gitignore` keeps `.env` out. `synalog.toml`
does, so a team shares one database by name; the tables do too, and that is the point — they tell whoever installs the layer which
data it expects.

In [Lemma](https://github.com/SynaLinks/lemma), a workspace's own
layer — its database, one folder named after the workspace,
`layer/<workspace>/` — is already a git repository with every change
committed. Push it, and the workspace's definitions can be installed in any
project. The other way round, a Lemma workspace installs layers from
repositories beside its own, each connected to its own database.

## Keeping up

```shell
uvx semantic-layers list      # the installed layers: where they came from, whether you changed them, whether they are connected
uvx semantic-layers update    # bring them to their source's latest version
uvx semantic-layers check     # verify every layer with synalog — or one: check sales
uvx semantic-layers search 'churn|retention'   # find definitions by name, keywords and description (a regex)
```

`update` never overwrites a layer you modified: it keeps it and says so.
